# Cooperative parallel pull requests; merges and per-PR pushes stay serialized

## Question

The kit launched with one designated branch and one open PR at a time. With
multiple builders, is the single open slot a safety property or a
bottleneck?

## Decision (the Patron ruled, 2026-09-19: "with multiple builders there
should be cooperation and not limitations of only one PR open at a time")

**Concurrent open PRs are the default**: one branch + one PR per unit,
admitted while its leased surface is disjoint from every other open PR's.
Serialization survives only where it is load-bearing: never push to a
branch whose checks are running (the measured 11-cancelled-runs lesson);
the Maestro merges one at a time with the next PR rebasing first; shared
derived files stay fragment-safe. Hosts whose standing rules mandate a
single designated branch run single-slot mode, recorded per host.

## Why

The original slot conflated three protections (check-cancelling pushes,
merge races, derived-file collisions) with a fourth thing that was never a
protection: making finished work queue. The three protections survive as
named rules; the queue does not.

This amends the reconciliation record's single-slot reading (docs/RECONCILIATION.md): the measured protections it derived survive as named rules; the queue itself was never one of them.

## Revisit if

Merge-queue depth or cross-PR rebase churn measurably exceeds what the old
single slot cost in idle builders.
