# Assimilation authors the context, the Patron's review governs it, and FLOW measures the work

## Question

Three gaps in one Patron directive (2026-09-21). First: adoption inventoried
the eight runbook functions but never hunted the documents the engteam
actually works FROM — requirements, design, technology, data, integration,
environments, security, testing, SOPs, diagrams — and authored nothing where
the host had nothing, so an assimilated repo started with silent context
holes. Second: the review loop had sign-off but no structured dissent — the
Patron could ack a version or stay silent, with no recorded way to say
"correct this, remap that, let's discuss" — and no way to feed the
retrospective directly. Third: the Foreman measured and the Maestro paced
with no instrument — velocity, estimated-vs-actual sizing, quality and
burndown existed as ledger events nobody folded.

## Decision

1. **The context hunt.** `/adopt` sweeps the host for the ten context
   functions (many→one mapping like every function), and where a function
   has NO document, **authors an evidence-cited draft** — derivation-first,
   every claim citing the tree, gaps written as open questions in the
   document, never invented facts. Every mapped record and every authored
   draft is registered in `documents_of_record`, so an assimilation arrives
   with its whole review queue visible on the DOCS tab as never-reviewed.
2. **Feedback is a first-class review answer.** `wall ack-doc <path>
   --feedback "..."` writes `doc_feedback`; the doc reads **feedback-open**
   (outranking every readable state) until a NEWER ack lands, and the text
   routes to the Architect as a finding. Signed documents are the engteam's
   **context markers** — designs cite them, gaps they expose become
   questions or arcs, and every new version voids the previous sign-off
   (the sha rule of DEC-0026, unchanged).
3. **The Patron feeds the retro directly.** `wall retro-note --text "..."`
   writes `retro_input`; pending inputs surface on the RETRO tab, and the
   next retrospective must address each one — adopted, queued, or declined
   with a reason.
4. **The FLOW tab** folds the EXISTING item stream (`item_created`,
   `item_state` with §8 estimate/actual, `item_shipped`) segmented by
   `retro_held` boundaries into per-iteration velocity, estimate-vs-actual
   points (XS=1 S=2 M=3 L=5 XL=8 — a convention, held consistently), bugs
   filed, and open-at-close burndown. No estimates recorded renders as
   "none recorded", never an invented number. No new events — measurement
   reads what the discipline already writes.

## Why

The reconciliation record's core lesson again, at three altitudes: evidence
over self-report (G0b). A repo's context that lives in heads is
self-report; an authored, evidence-cited, sha-signed document is checkable.
A Patron objection spoken in passing is self-report; `doc_feedback` is a
record with a route. A wave that "felt fast" is self-report; FLOW's
iteration table is the count. And the derive-first authoring rule is
PRODUCT_INTAKE §2 applied to documents: most answers are already in the
tree — the draft's job is to cite them, and to say plainly where the tree
is silent.

## Revisit if

- Authored drafts accumulate unreviewed across waves — then the review
  queue, not the authoring, is the bottleneck; batch the review into wave
  close before authoring more.
- The point scale distorts sizing (hosts using time or throughput units) —
  make the scale a config key rather than changing the convention ad hoc.
- Feedback threads need more than one round (feedback → fix → feedback) —
  consider folding the doc's full review history, not just the latest ack
  and feedback.
