# A program lead per engineer and a fleet operator per machine; the engineer stays the Patron for every consent gate

## Question

The roster was built around one repository: one Maestro, one wall, one
Patron. Running the roles for a day across several adopting repositories on
one workstation showed what that leaves unowned. Nobody decided which
repository's work came first. Green PRs sat unmerged because each driver
reported green and ended, and no session owned the merge. Two sessions in one
repository both bumped the version. And the machine itself ran out of memory
and cores, because agent services, a local model server, reviewer clients and
self-hosted runners each sized themselves as if alone, while a watchdog kept
restarting services the owner had turned off (FAILURE_PATTERNS F-OPS-011 to
F-OPS-013, F-GIT-005, F-REVIEW-013, F-PROC-004, F-PROC-005).

The owner asked for the engineering team to work as their position:
"incorporate and improve the eng team ... functioning as my position and
organizing and driving product design, architecture, maestro, foreman,
researchers, and we create any new roles we need." Which new roles, what may
they do, and where does their authority stop?

## Decision

The Patron (the owner, in writing, 2026-09-29). The split was proposed as:

> "I lead as program lead/Maestro across all repos ... you stay the Patron for
> anything that turns things on on your box, deletes, widens access, spends
> money, or goes to production"

and the owner answered: **"Yes, that split"**.

1. **Program lead** (`.claude/agents/program-lead.md`), one per engineer,
   across every repository that engineer owns. It acts for the engineer day to
   day: product design direction and architecture priorities across
   repositories, the cross-repo queue, assignment of work to each
   repository's Maestro, and merging green PRs within the rules. It works
   through each repository's Maestro and wall, never around them.
2. **Fleet operator** (`.claude/agents/fleet-operator.md`), one per machine.
   It observes the machine's resources and services (the throttle plan,
   agent services, runners, local model servers), turns findings into
   recommendations with numbers, and applies only reversible, lower-only
   changes inside the plan's floors, with an override window. It never
   starts, enables or raises anything, and never deletes.
3. **The Patron consent gates stay the engineer's.** No role, including the
   Program lead, takes any of: starting or enabling anything on a machine;
   deleting; widening access; spending money; production. Roles prepare these
   decisions; the engineer makes them.
4. **One merge seat per repository.** G12 is amended, not replaced: merge and
   ready-flip belong to the holder of the repository's merge seat, which is its
   Maestro by default, or the Program lead when it records that it took the
   seat. Pushes and merges serialize through the seat holder's queue. The
   check-in merges green; a driver's report is not the merge.
5. **The version bump moves to integration time.** The Integrator bumps the
   version after the rebase onto the moved main (Integrator step 1b), or the
   Maestro or Program lead assigns numbers up front.
6. **No release manager.** The Integrator already owns a unit's path from
   built to mergeable, and item 5 closes the only gap found (two units racing
   one version number). A separate seat would add a hand-off, not an owner.
7. Neither new role is a per-repository singleton, so neither is in
   `SINGLETON_ROLES`: the registry is per repository and cannot count them.
   The limit is procedural. Their keys use the `prl` and `fop` prefixes.

## Why

Every failure in the day's record was a duty with no single owner, or a duty
owned by a process that could not see the owner's intent. The Program lead
owns the cross-repository duties (order, direction, the merge that nobody was
taking) without adding a second dispatcher inside any repository. The Fleet
operator owns the machine the way the Foreman owns the wall: it measures and
recommends, and the only thing it may do on its own is turn a knob down.

Keeping the consent gates with the engineer is the same asymmetry that makes
the Warden safe (block, never grant): a role that can act for the engineer is
safe to run exactly when it cannot turn things on, delete, widen, spend or
ship to production on its own.

## What this rules out

- A Program lead that dispatches Builders into a repository past its Maestro,
  or merges in a repository whose seat another live session holds.
- Two merge seats in one repository at once.
- A Fleet operator, watchdog, reconcile or installer that starts, enables or
  raises anything, or restarts a service that stopped cleanly or was disabled.
- A deletion that is not owner-run, or that leaves no recorded way back.
- A "no push while any CI runs" rule stated over every session sharing a
  repository's CI.
- A dedicated release-manager role.

## Revisit if

- The platform merge queue in `docs/FLEET_COORDINATION.md` is adopted: the
  merge seat then becomes "the session that enqueues", and item 4 should be
  re-read against it.
- The coordinator is built: the Program lead's cross-repo queue and the
  one-per-engineer limit could become coordinator state and be enforced there.
- A second engineer shares a repository: the Program lead is one per engineer,
  so two of them can meet in one repository, and the seat rule must name how
  they hand the seat over.
- Releases start shipping several units together, and the Integrator's
  per-unit bump stops being the natural place for the version.
