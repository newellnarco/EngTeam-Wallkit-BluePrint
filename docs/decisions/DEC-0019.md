# The wall speaks MCP: six tools exactly, stdio only, schemas from contracts

## Question

The Patron's direction (2026-09-20, verbatim): *"this engineering team
and wall and project and its blue prints all need to be able to run via
vs code integration and other interfaces like cursor. the local
dev/engineer should basically answer or provide information or new
instructions via that mcp integration on claude code, on claude.ai,
cursor, vscode or others. and stay completely up to date via a wall and
other reporting dashboard mechanisms."* What exactly does the wall
expose over MCP, on what transport, and under which of the standing
charters?

## Decision

`tools/wall/mcp_server.py` — one stdio MCP server every MCP client
(Claude Code, Cursor, VS Code, agent harnesses) attaches to. Four
binding clauses:

1. **The tool set is an exact allowlist — these six, and growing it is
   a decision, not an edit** (the DEC-0004 relay discipline, applied to
   tools):
   - `wall_status` — the summary, THE SAME `summary.build_summary` the
     `wall summary` CLI prints (DEC-0018: one implementation).
   - `wall_item` — one board item by id, from the derived snapshot.
   - `wall_waiting` — the human-queue asks + open-question count: what
     the wall needs the ENGINEER for.
   - `wall_trace` — the `wall trace` CLI, captured verbatim.
   - `wall_answer` — the engineer resolving a human-queue question:
     the `wall answer` CLI captured, refusals included (an already-
     answered question is refused here exactly as at the terminal).
   - `wall_enqueue` — the one write beyond the ledger: the DEC-0004
     host-queue add, built from `contracts.EnqueuePayload` and sent to
     the host's own allowlisted endpoint; honestly unavailable when
     `queue_api.origin`/`add` are unconfigured.
2. **Reuse over reimplementation** (DEC-0018 clause 2, as mechanism):
   the read tools serve the same folds the CLI and the page serve, and
   the verb tools CAPTURE the existing CLI commands — the MCP surface
   is a second presentation of the same implementations, so an editor,
   a terminal and an agent can never disagree.
3. **Stdlib only, stdio only** (DEC-0017): the protocol subset MCP
   needs (initialize / tools/list / tools/call / ping, newline-
   delimited JSON-RPC) is carried without an SDK. **Remote (HTTP)
   transport — what claude.ai's custom connectors would need — is
   explicitly out**: it crosses the local-only line every deployment
   document assumes, and adopting it is a superseding DEC, not a flag.
4. **Where this sits in the roles: it is the ENGINEER'S SEAT, made
   portable — not a new role.** The Patron already has these verbs at
   the terminal (`wall summary`, `wall answer`, the EXECUTE click);
   MCP is the same seat reachable from any editor. That makes role
   enforcement structural: `--role engineer` (the default, for the
   human's editor configs) serves all six tools; `--role agent` (for
   agent harness configs) serves the four READS only. `wall_answer`
   writes to the `s_human` shard — an answer from that shard IS the
   record of the engineer speaking — so an agent must never hold it:
   an agent that could call it would be forging a human ruling.
   `wall_enqueue` is likewise the engineer handing out work; agents
   receive instructions THROUGH the queue, they do not issue them to
   themselves. A role asking for a tool outside its allowlist is
   refused by name, and an unknown role degrades to `agent`, never up.
5. **Failures are results, not crashes.** A tool error returns
   `isError: true` with the reason; a malformed client line gets a
   parse error and the loop continues — one bad message must not kill
   the server every editor is attached to.

## Why

One stdio server is the whole multi-editor story: MCP is the protocol
those editors already speak, so per-editor integrations would be N
copies of this file with N drifts (the RECONCILIATION class again).
Capturing the CLI rather than reimplementing it keeps the engineer's
verbs identical at the terminal and in the editor — same refusals, same
transcripts — which is what makes the audit trail one trail.

## Revisit if

- A seventh tool is genuinely needed (name its derivation per DEC-0018
  clause 4, then supersede).
- claude.ai-direct access is wanted (remote transport DEC: auth story,
  exposure boundary, and which of these tools survive the trip).
- MCP's stdio framing changes in a way the hand-rolled subset misses
  (the tests speak the wire protocol against a spawned server, so this
  surfaces as a test failure, not a field report).
