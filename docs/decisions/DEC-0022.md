# Dependencies are verified and named at install; uninstall is a first-class mode

## Question

Two follow-ons to the DEC-0021 bootstrap, both the Patron's
(2026-09-20, verbatim): *"also make sure any dependecies tools, apps,
etc...are all included in our install or upgrade"* and *"we also need
to consider an uninstall?"* What does "dependencies included" mean for
a kit whose portability charter forbids bundling anything (DEC-0017),
and what may an uninstall delete?

## Decision

1. **"Included" means VERIFIED AND NAMED, because bundling is the thing
   DEC-0017 exists to prevent.** Every bootstrap mode that installs or
   upgrades runs a preflight that checks the kit's real dependency
   surface and says, per item, what it is for and where to get it:
   Python 3.11+ (the one hard dependency — a too-old interpreter fails
   an `--apply` by name), git (a WARNING, never a blocker: stamps
   degrade to `unknown` honestly, `wall ship` and upgrade deltas name
   it when they need it), and the note that everything else is stdlib —
   no pip installs, ever. Optional surfaces bring their own host and
   the preflight says so: an MCP editor for the engineer seat, a
   browser for the wall, the platform scheduler for the timer (which
   `wall install` names per platform). A dependency that appears
   without joining this preflight is drift.
2. **`bootstrap.py remove` is the uninstall, with the audit record
   protected by default.** It un-vendors the machine (`tools/wall/`,
   `frontend/theme/`, `templates/`) and strips exactly the wall's own
   entry from each MCP client config (other servers kept; a config
   that held only the wall is removed; invalid JSON is not ours to
   touch). **The ledger survives by default**: `.wall/` — events,
   config, registry — is the audit trail, and an audit trail deleted
   by default is not an audit trail; only an explicit `--purge-state`
   deletes it. Never touched by any flag: the context documents and
   `docs/` (by uninstall time they are the host's documents, whoever
   seeded them — a script deleting the host's rules is the DEC-0021
   boundary crossed in reverse) and the host's decision log. Dry-run
   default, `--apply` to do it, same as every mode.
3. **What a script must not uninstall stays named:** the machine timer
   (`wall uninstall` runs BEFORE removing `tools/wall` since it needs
   the adapter code — DEC-0010's consent discipline applies to removal
   exactly as to creation), and the deliberate deletion of documents.

## Why

An install that assumes its dependencies produces the failure on the
adopter's machine at the worst time; a preflight that names them
produces it in the first ten seconds with the fix attached. And an
uninstall that defaults to deleting the ledger would let one command
end the auditability the whole kit exists to provide — reversibility
means the KIT leaves cleanly, not that the record of what it did
leaves with it.

## Revisit if

- The kit ever gains an optional component with a genuine third-party
  dependency (DEC-0017's adapter clause): its preflight entry and its
  removal step land in the same DEC that admits it.
- Adopters want `remove` to also revert vendored `docs/` (then: a
  manifest of kit-owned vs host-touched files, not a guess — and the
  reconciliation discipline decides).
