# Fast-track ends in a pull request, never straight to the default branch

## Question

Open question 8. A doc-only change skips reviewer dispatch, test authoring and
most of CI. Does it also skip the pull request?

## Decision

No. Fast-track is a **route**, not a destination. Every change rides a pull
request opened under the owner's identity, draft, then merged by the
coordinator once its (scoped) checks are green.

Fast-track means: no reviewer dispatch, no architect sign-off, no test
authoring, and whatever CI reduction the host repository's own scoping already
provides for documentation changes.

## Why

A uniform audit surface is worth more than the seconds saved. Every change has
the same shape - branch, pull request, checks, merge - so there is exactly one
procedure to learn, one place to look for what happened, and nothing special to
remember when a change turns out to be less doc-only than it looked.

It also survives branch protection cleanly, which the straight-to-default route
does not.

Classification stays mechanical and stays out of the agents' hands: computed
from the changed file set, never asserted by the agent doing the work. If an
agent can declare its own route, every builder eventually discovers that calling
its work documentation skips the gates. Deny beats allow, always; a mixed
changeset splits rather than getting an exception.

Answered against the reference deployment's standing policy in
`docs/RECONCILIATION.md` Q8: every change rides a pull request, opened under the
owner's identity, draft, then merged once its scoped checks are green.

## What this rules out

- Direct pushes to the default branch by agents, for any reason.
- An agent-declared route.
- A per-change CI exception negotiated in prose.

## Revisit if

The host repository's checks become so cheap that even the classification is
not worth the code. The pull request stays regardless.
