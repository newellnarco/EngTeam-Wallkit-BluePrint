# Evidence outranks self-report

## Question

An agent reports that it is working, that its checks are green, that its unit is
done. How much of the system's state may be built on what agents say about
themselves?

## Decision

None of it. Status is derived from the repository, the tests and the check runs.
Agent statements are inputs to be verified, never the record.

Mechanically:

- A run with a start record and no terminal record past its deadline is
  **stale**, regardless of what its last message claimed.
- Item files are a materialized view of the event log, so `wall diff-state`
  catches anything written out of band.
- Before accepting a report of a check result, read the check.
- Before accepting *or* declining a review finding, verify it; prove the
  disagreement when you decline.

## Why

It is the only rule that keeps working when an agent is wrong in good faith,
which is the common case. Nothing here assumes bad behaviour: an agent that
believes its checks are green because it read a stale page is indistinguishable,
from the outside, from one that is right.

Measured in the reference deployment's first wave: a builder's own report of its
draft checks was superseded twice by reading the check runs directly, and an
attestation job's first live run disproved a claim the design had refused to
assume (`docs/RECONCILIATION.md`, G0b).

The same principle runs through the plumbing, not just the crew - a heartbeat
exists because a dead timer and a quiet project look identical from the outside.

## What this rules out

- A wall panel whose source is an agent's description of itself.
- Merging on a report rather than on a read check.
- Trusting a run that says it is fine past its deadline.

## Revisit if

Never. This is the rule the rest of the design is arranged around; changing it
means changing what the wall is for.
