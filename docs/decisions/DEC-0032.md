# The DOCS tab reads the document and takes the verdict

## Question

The DOCS tab (DEC-0026) showed review STATE — current, CHANGED,
never-reviewed, feedback-open, missing — but the Patron observed
(2026-09-22): there is no link to the documents themselves, no way to
read one from the wall, and no way to approve, deny, or require
modification from where the state is shown. And when a verdict is deny
or request-changes, how does the required work carry back to the crew —
across Claude Code, Cursor, VS Code, or any other MCP client?

## Decision

1. **The courier writes `derived/docs.json`** alongside the snapshot:
   every registry document's path, sha, and text (capped at 150k
   characters with the truncation stated), with honest nulls and a note
   for a missing or unreadable file. Derived, never live-read: the wall
   keeps rendering from courier output only, so page and snapshot can
   never disagree about what was reviewed.
2. **The server allowlist grows by exactly that one name.** Five exact
   filenames now; still no prefix rule, no directory listing, still
   127.0.0.1 (DEC-0004). Serving repo files by arbitrary path was
   considered and rejected — the allowlist's whole point is that the
   next thing to land in the derived dir is NOT served.
3. **Every DOCS row opens a read-in-place popup** — the document's text,
   a truncation note when capped, and a drift note when the file's sha
   has moved since the snapshot — with **APPROVE / REQUEST CHANGES /
   DENY** and a reason box (reason mandatory unless approving). From
   `file://` or with the server down, the popup degrades honestly: it
   names `wall serve` and the `wall ack-doc` CLI instead of showing a
   spinner.
4. **The buttons only ENQUEUE (DEC-0030 held).** The verdict is a typed
   `doc_review` directive — `action: approve|changes|deny`, `path`,
   `sha` as read, `reason` — validated in `contracts.py` and sendable
   identically from the wall popup and from any MCP client via
   `wall_enqueue` (DEC-0019's six tools, unchanged in count). The
   consumer closes the loop: approve becomes `wall ack-doc <path>` at
   the sha that was read (sha moved = refuse and re-read); changes and
   deny become `wall ack-doc --feedback "<reason>"` PLUS a fix item
   filed through the normal finding route. That is the carry-back: the
   doc reads feedback-open, and the fix story is visible to every
   surface through `wall_status` / `wall_item` until a newer ack lands.

## Why

"Reviewable by the Patron" was a mechanism only for a Patron already at
a terminal; the wall showed that a review was owed while the reviewing
itself required leaving the wall. RECONCILIATION grades claims by how
they are held up: a review state with no path to the document holds up a
claim ("this doc was reviewable") the page could not actually support.
The typed directive keeps the wall's one hard law — it never mutates
state — while making the verdict a first-class queue citizen, so the
same contract serves the popup and every MCP editor without a bespoke
channel per client.

## What this rules out

The wall writing `doc_reviewed` events itself (it enqueues, the consumer
acks); serving documents by live path (only courier-derived `docs.json`
is served); a per-editor webhook or side channel (one queue, one
vocabulary, N clients); an ack recorded at a sha the reviewer did not
read.

## Revisit if

- A registry document exceeds the 150k cap in practice — pagination or
  a per-doc fetch is a superseding decision on the allowlist.
- The queue API grows authentication — the verdict should then carry
  the reviewer's identity instead of the courier inferring it.
- MCP clients need to READ documents through the wall server rather
  than from their own checkout — that is remote exposure, DEC-0019's
  revisit clause.
