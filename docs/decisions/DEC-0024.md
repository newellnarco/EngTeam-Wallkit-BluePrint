# Two test lineages, five families, and usability as a gated requirement axis

## Question

The kit demanded citable acceptance criteria and tiered tests, but never named
the two distinct test lineages — tests that validate the PRODUCT OUTCOME (does
it do what the user needed) versus tests that verify the DESIGN (is it built
as architected) — so a suite could be all one kind and read as complete.
Non-functional concerns (guardrails, data integrity, security, scalability,
performance) had partial homes but no declaration point where an arc states
which apply. And human usability — fewer interactions, actionable states,
legibility, aesthetic coherence, workflows that never end in a ditch — was one
intake question, not a requirement axis anything gated on. What names these,
and where do they bind?

## Decision

1. **Every expected test names its lineage** (TESTING_STANDARDS §1b):
   validation cites the outcome (intake answers, `AC-n`, a named trajectory);
   verification cites the design (`docs/architecture/` section, `DEC-NNNN`,
   schema). The story's test expectation carries the lineage per test, so a
   one-lineage suite is visible at authoring time.
2. **Five non-functional families are declared per arc** — guardrails, data
   integrity, security, scalability, performance — by the Architect, at
   design time (ITEM_AUTHORING §3.8). A family declared inapplicable is a
   recorded declaration with a reason, never an omission.
3. **Usability is a requirement axis** (`docs/UX_STANDARDS.md`): user-facing
   stories carry countable usability criteria (interaction budgets,
   actionable states, token-derived legibility, aesthetic coherence);
   user-facing arcs name their basic / advanced / recovery trajectories;
   every trajectory terminates in success or a recoverable, explained state —
   the four ditch prohibitions (no dead ends, no silent data loss, no
   misrepresentation, no unnecessary complexity) are written as must-never
   criteria with sweeping tests. Quickstart, user guide and in-app help move
   with the code via DOCS_MAP rows. The owner's LOOK (the verification queue)
   is the final aesthetic judge — the one call never automated.

## Why

Patron direction, 2026-09-21. The reconciliation record already carried the
seed of each half: the source-mapping law (a criterion cites the design OR the
outcome — RECONCILIATION's ambiguity classes are mostly one lineage missing
its source), and the first wave's finding that "built as specified" and "not
what was wanted" happen simultaneously when only one lineage exists. The
usability half extends the same citability discipline to the qualities users
feel: a countable interaction budget is testable; "friendly" alone is not —
so the standard states each quality at the level a test or the owner's eye can
decide it.

## Revisit if

- The lineage field becomes rote (every story mechanically tagging both
  without the tags catching a gap) — the signal has decayed into ceremony.
- A sixth family recurs across adoptions (accessibility is the likely
  candidate) — graduate it into TESTING_STANDARDS §1b the way templates
  graduate.
- A host has no user-facing surface at all — UX_STANDARDS declares itself
  inapplicable there, and that declaration should be one line, not a debate.
