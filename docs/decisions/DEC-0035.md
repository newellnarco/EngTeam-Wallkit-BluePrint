# A second CI trigger path is a project's choice, paired with one collapsing group

## Question

A mined lesson says a merge gate should be reachable from two events (pull
request, and push to the working branch) so that a platform outage that stops
creating pull-request runs cannot let a change merge with no CI. The kit's
F-CI-001 scoped `push` to the default branch whenever pull requests gate
merges, its class-guard failed exactly the two-trigger configuration, and
`FAST_TRACK` names push-on-every-branch the costliest blowout in the corpus.
Which rule stands?

## Decision

The Patron (2026-09-23): **the rules change; this kit's own CI does not.**

1. **A second trigger path is allowed as a deliberate project choice.** A
   project may add `push` on working branches beside `pull_request`.
2. **Only with one collapsing group.** Both events for one branch resolve to
   one concurrency group that cancels the superseded run, and a test
   evaluates the group under both payloads and asserts they are equal
   (F-CI-002). The group is keyed on the head repository AND the branch
   name, so a fork's pull request from a same-named branch never shares a
   group with this repository's branch and cannot cancel its run:

   ```yaml
   concurrency:
     group: ${{ github.workflow }}-${{ github.event.pull_request.head.repo.full_name || github.repository }}-${{ github.head_ref || github.ref_name }}
     cancel-in-progress: ${{ github.ref_name != github.event.repository.default_branch }}
   ```

   The one case it still joins is two pull requests from the same branch of
   this repository into different base branches. A project that opens those
   adds the base ref to the key, and accepts that its push and pull-request
   runs then no longer collapse. `tests/test_ci_group_recipe.py` evaluates
   this recipe under each payload. Runs on the default branch are never
   cancelled: each one is the record of what merged.
3. **The cost is recorded, not hidden.** Branches with no pull request then
   bill runs; the project records that as an accepted cost.
4. **The default is unchanged.** Without that choice, `push` stays scoped to
   the default branch. This repository's `.github/workflows/ci.yml` keeps the
   default.

Applied in `templates/FAILURE_PATTERNS.md.template` F-CI-001 (check and
class-guard) and F-CI-002, `docs/FAST_TRACK.md`, and `SKILLS_LIBRARY` 8.14.

## Why

RECONCILIATION's measured lesson is that a gate which can silently not run is
not a gate. Both failures were paid for: a merge with no CI when the only
trigger went quiet, and a budget blown by uncollapsed duplicate runs. The rule
had guarded only the second. Pairing the extra trigger with a collapsing group
guards both, and leaving it a project choice keeps the cheaper default for
projects that do not need it.

## What this rules out

Push on working branches with a concurrency group keyed on `github.ref`
(which differs between the two events); a second trigger with no test of the
group; changing this kit's own CI under this ruling.

## Revisit if

The platform offers a native fallback for dropped pull-request runs, or a
project measures the extra cost of branch pushes as material.
