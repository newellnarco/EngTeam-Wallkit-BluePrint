# One-command bootstrap; the kit lives as a bounded subtree beside the product

## Question

The runbooks (empty-repo, existing-repo adoption, upgrading an
adoption) were correct but MANUAL — a first-time engineer on a fresh
machine, VM, container, cluster node or cloud box had to execute prose.
And the kit's placement in a product repository was practiced (the
reference adoption's `tools/wall/` + `.wall/` + process docs) but never
ruled.

## Decision

The Patron's direction (2026-09-20, verbatim): *"make sure any new
environment or session, using local pc, vm, docker, cluster or cloud
server and the God engineers use of their preferred integration
interface is as simple and clear and as automated as possible and
doesnt require them to do much more than run some scripts or code, load
this into a side repo, separated but same repo as their product, and
additional steps for an existing/assimilation deployment of this kit.
as well as the upgrade path."* Four binding clauses:

1. **The side-repo layout is the rule:** the kit lives as a **bounded
   subtree inside the product repository** — `tools/wall/` (the
   machine), `docs/` (process corpus + decisions), `frontend/theme/`,
   `templates/`, plus the `.wall/` state skeleton — separated from the
   product's code, versioned with it, never a second repository to
   keep in sync and never files scattered through the product tree.
   Only the context documents the templates become live at the root,
   because the root is where an entry point belongs.
2. **The runbooks are one command each:** `tools/wall/bootstrap.py`
   `fresh` (empty-repo runbook: vendor the subtree, materialize
   `.wall/`, copy MISSING context templates — never over an existing
   file, stamp the kit source), `adopt` (existing-repo runbook:
   automated inventory of what already serves each adoption function
   by the names those things go by, machine vendored, host documents
   untouched and gaps named), `upgrade` (the README upgrade path:
   verbatim re-vendor, upstream commit range since the stamp shown,
   decisions-first reminder). It runs from the kit checkout with
   nothing installed — stdlib only (DEC-0017) — so the same command
   works on a laptop, a VM, in Docker, on a cluster node or a cloud
   box; the deployment targets differ only in who runs the timer
   (DEPLOYMENT_TARGETS.md).
3. **The engineer's interface is emitted, not hand-written:** `--mcp
   claude-code cursor vscode` writes (or additively merges) each
   client's config pointing at the wall MCP server with `--role
   engineer` (DEC-0019). Preferred-interface setup is part of
   bootstrap, not a follow-up chore.
4. **Consent is the default, still:** every mode is a dry run that
   prints exactly what it would do; `--apply` does it. What stays
   manual stays manual **on purpose** — RULES.md Part 1 (the hard
   rules need a human), `wall install` (a machine timer needs explicit
   say-so, DEC-0010), and arming `queue_api` against a real endpoint
   (a write surface needs its host's ruling, DEC-0004's lesson).

## Why

Prose runbooks are correct exactly once — at review time. A script IS
the runbook, kept honest by tests, and a dry-run-first script preserves
the consent discipline while removing the transcription errors. The
side-repo ruling writes down what the reference adoption already
proved: one bounded subtree upgrades verbatim, diffs cleanly, and never
argues with the product about whose file a path is (the same
one-authority shape as RECONCILIATION's G-series and DEC-0018).

## Revisit if

- An adopter needs the kit OUTSIDE the product repo (a true sibling
  checkout): the stamp and upgrade flow would need a path indirection —
  a superseding DEC, not a flag.
- Bootstrap grows a step that writes host documents: that crosses the
  adopt mode's "host documents untouched" line and reopens clause 2.
