# Event shards ship on an isolated branch, never on the development branch

## Question

Open question 7. The event log is the audit trail, so it has to be durable. Does
`.wall/` live in the target repository, and do the shards get committed?

## Decision

`.wall/` lives in the **target repository**. Event shards are **gitignored in
the working tree** and shipped as snapshots to a dedicated telemetry branch by
the courier, using an isolated index so the working tree and the current index
are never touched. No pull request ever carries a shard.

## Why

Committing shards on the development branch was the original design and it is
wrong for a repository that ships through a one-pull-request-at-a-time pipeline.
Shards are high-churn by construction - they change every minute, from several
sessions at once - so they would ride every pull request and conflict
constantly. That is the same class of pain that forced the reference deployment
to invent per-change fragment files for its board state: derived, high-churn
content in the pull-request path makes every concurrent change collide on files
nobody edited on purpose.

The isolated-branch pattern keeps all three properties that mattered:

- **Durability** - the snapshot is a real commit on a real branch, fetchable.
- **Reproducibility** - merge is still idempotent on `event_id`, so a rebuild
  from shards is byte-identical whether they came from disk or the branch.
- **Isolation** - an isolated index write cannot disturb an in-flight edit.

The pattern is not theoretical; it was already running in production for status
streaming before the kit adopted it (`docs/RECONCILIATION.md`, Q7).

## What this rules out

- Shards in a pull request, in any form.
- Derived output (`.wall/derived/`, logs, run artifacts) in version control at
  all. It is reproducible and it conflicts every sweep.
- A separate repository for `.wall/`. Simpler to install and the audit trail
  sits beside the code it describes; split later if a second project needs a
  shared view, which is a migration rather than a redesign.

## Revisit if

Several repositories need one cross-repository ledger. The machine-wide walker
(DEC-0010) already gives the cross-repository rollup, so this would be about
storage, not visibility.
