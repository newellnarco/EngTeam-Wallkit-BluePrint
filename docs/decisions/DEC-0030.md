# The regime lifecycle: the scan recommends, the Patron decides, the Warden audits — all on the ledger

## Question

DEC-0028 gave the kit a regime register the Patron selects into and
self-attests against, but nothing DETECTED which regimes the code suggests,
nothing named the tension when a recommended regime was disabled, and an
audit had no shape — attestations trickled in one control at a time with
notes optional outside waivers. The Patron directed (2026-09-22): the Warden
runs periodic repo checks identifying which regimes are needed; the dashboard
shows which are active, inactive and recommended and lets the user enable or
disable them; disabling something recommended shows a "not recommended for
disabled" disposition with a popup explaining specifically why; enable
actions and audit requests dispatch to the Warden (MCP or HTTP); and the
audit output must contain passed, failed, waiver — each with proof or
reasons. Where do these settings and attestations live?

## Decision

**On the ledger, which is already the repo file of record.** No parallel
settings file: `compliance_scanned` (the Warden's evidence pass, per-regime
recommended + evidence verbatim), `compliance_selected` (unchanged from
DEC-0028 — the enable/disable decision with its reason), `compliance_attested`
(unchanged shape, tightened contract) and `compliance_audited` (the audit
marker) are ordinary ledger events; the fold derives the register, so every
decision and every audit ever run has an author, a timestamp and a diff.

- **The scan** (`wall compliance-scan`, run periodically by the Warden) is
  deterministic and dumb on purpose: word-boundary signal matching over
  tracked text, evidence lines naming file and signal, skipping the trees
  that talk ABOUT compliance (the vendored kit, `.claude/`, the blueprints,
  the decision log). It never flips a selection.
- **The disposition** folds scan against selection: `active`,
  `active (scan found no surface)`, `recommended -- decide`, `inactive`,
  and — loudly — `NOT RECOMMENDED FOR DISABLED` when a selection turns off
  a regime the code shows surfaces for. The WHY popout carries the scan's
  evidence verbatim; the tension stays named until the evidence or the
  selection changes. The decision remains the Patron's.
- **Dispatch** rides the EXECUTE port: ENABLE / DISABLE enqueue
  `{directive: "warden_regime", action, regime}`, REQUEST AUDIT (shown on
  active regimes) enqueues `{directive: "warden_audit", regime}`. MCP and
  HTTP converge on the same queue; the consumer — the Warden — acts and
  writes the events. The wall itself never mutates a selection.
- **The audit contract** (`wall audit <regime> --file results.json`):
  complete or refused by name — every control present, every row
  `pass | fail | waiver` PLUS a non-empty note (pass carries its proof,
  fail and waiver their reason). `wall attest` is tightened the same way:
  the waiver-only note requirement becomes universal.

## Why

The ledger already solved storage: it is versioned, authored, reviewable and
survives every restart, and RECONCILIATION's G0b (evidence over self-report)
demands exactly what the audit contract encodes -- a verdict is only as good
as the proof beside it. A parallel settings file would be a second source of
truth that can drift from the fold; a scan that could flip selections would
make the Warden the Patron. Naming the disabled-despite-evidence state as a
standing disposition follows the same reconciliation lesson: a decision made
against the evidence is legitimate, but it is never silent.

## Revisit if

- The scan's signal lists produce recommendations people learn to ignore
  (false-positive fatigue) -- tighten SCAN_SIGNALS or add per-repo config.
- A host needs per-control waiver EXPIRY -- today a waiver stands until
  re-audited.
- The queue port gains authentication -- the dispatch directives should then
  carry the requesting identity end-to-end.

## Consequences

The POSTURE tab becomes a control surface as well as a mirror, but its
authority is unchanged: it can only ask the Warden. A regime disabled against
the evidence is a standing, visible disposition rather than a silent
setting. The DEC-0028 challenge heuristics continue unchanged alongside the
dispositions.
