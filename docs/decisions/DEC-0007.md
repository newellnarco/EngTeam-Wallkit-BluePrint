# Builders are tiered by task class

## Question

Open question 11. Builders are the dominant cost line. Run them all on the
strongest model, or tier them by what the work actually needs?

## Decision

Tier. The coordinator tags a task class at dispatch; mechanical work goes to the
verification-tier model, high-ambiguity or high-blast-radius work to the
execution tier.

Mechanical, by default: documentation sweeps, filing and bookkeeping changes,
status flips, template fills, mechanical refactors with a test already in place.

## Why

Measured, not estimated. In the reference deployment's first wave every builder
ran on the strongest model and consumed 400,000 to 720,000 tokens per unit -
roughly three million across six units, for work that included several passes
that were purely mechanical.

The tiering is cheap to get wrong in the safe direction: a mechanical task that
turns out to be ambiguous escalates by raising a question, which is a mechanism
that already exists for other reasons.

The ledger records `model_requested` and `model_used` separately, so the
history stays honest when safeguards route a request elsewhere. Storing the
intent instead of the fact makes every per-model cost number wrong.

Measurements and the decision to tier: `docs/RECONCILIATION.md` Q11.

## What this rules out

- A single model constant for all builders.
- Inferring per-model cost from what was asked for rather than what ran.

## Revisit if

The price gap between tiers closes, or the escalation rate from mechanical
dispatches climbs high enough that the retries cost more than the tier saves.
Both are measurable from the ledger; check before arguing.
