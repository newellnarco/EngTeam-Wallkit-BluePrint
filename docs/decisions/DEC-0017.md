# Portability is a standing requirement, mechanically ratcheted

## Question

The kit's founding promise is "dependency-free scaffold that drops into an
empty repository — or an existing one". As capability seams grow (the
EXECUTE/AGENTS host integration, the planned typed-contracts module and
MCP adapter), does that promise stay prose in the README, or does it
become a binding, tested requirement — and what exactly does it require?

## Decision

The Patron's direction (2026-09-20, verbatim): *"Make sure all of it is
portable. the EngTeam Repo should be useful and deployable without a
major effort to any local machine, server, docker or cluster fresh clean
install, or deployed and assimilate anything similar that was there."*
That is now a standing requirement with four binding clauses:

1. **Stdlib-only is load-bearing, and ratcheted.** Every Python module
   under `tools/` imports only the standard library or the kit's own
   modules. This is enforced by `tests/test_portability.py` (an AST walk
   over every module, not a per-file string check), so a dependency
   cannot arrive silently. A future capability that genuinely needs a
   third-party package must be a **separate, optional, consent-gated
   adapter** whose absence costs nothing — and needs a DEC of its own.
2. **Fresh install anywhere, without major effort.** The supported
   targets and their documents of record: local machine —
   [`INSTALL.md`](../INSTALL.md) (Windows scheduled task / macOS
   LaunchAgent / Linux systemd-or-cron adapters, one machine-wide timer,
   `WALL_HOME` isolation); server / VM / Docker / Kubernetes —
   [`DEPLOYMENT_TARGETS.md`](../DEPLOYMENT_TARGETS.md) (worked
   Dockerfile, sidecar and cluster patterns, the five invariants every
   target keeps). A tooling change that alters an install or serve path
   updates those documents in the same change.
3. **Assimilation, not replacement, on an existing setup.** Deploying
   onto a repo that already has similar machinery (its own tracker,
   rulebook, roster, checklists) follows the `/adopt` runbook and
   [`RECONCILIATION.md`](../RECONCILIATION.md): inventory function by
   function, keep the host's document of record where one exists, fill
   only genuine gaps, and record collisions as decisions. The reference
   adoption (its DEC-0001..0004) is the reference execution — six of
   eight functions mapped to existing host documents, two created,
   nothing duplicated.
4. **New seams inherit all of the above.** The typed-contracts module
   ships stdlib-only inside `tools/wall/`. The MCP adapter, if built,
   speaks stdio JSON-RPC from the stdlib or it does not ship in the kit
   core; host bindings stay config (`wall.json`), never code forks.

## Why

Portability is the property every other promise rides on: "resumes from
disk, not from memory" only helps if the disk contents run wherever they
land. A dependency-free tree is trivially container-, cluster- and
air-gap-friendly — the moment one pip install arrives, every deployment
document above grows a caveat and the 30-second sample render stops being
true on a clean box. Prose promises drift; the ratchet test cannot.

## Revisit if

- A capability genuinely worth a third-party dependency appears (then:
  optional adapter + its own DEC, never a core requirement).
- Python's stdlib drops something the kit relies on (`sys.stdlib_module_names`
  makes the ratchet version-aware, so this surfaces as a test failure).
- The kit grows a second language runtime (the frontend theme is static
  assets today; anything that needs a build step reopens this).
